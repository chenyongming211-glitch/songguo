# 松果AI v0.1 统一 Learning Submission 开发计划

## 1. 计划定位

本文档是 `docs/v0.1-unified-learning-submission-plan.md` 的实施版开发计划。

开发目标：

```text
把小程序从旧的 session 单会话入口，升级为统一 Learning Submission 主链路。
无论孩子提交多少道题，都先沉淀所有题的学习资产。
正确题记录掌握证据。
错误题记录错因和掌握风险，并进入错题队列。
松鼠博士逐题陪练所有错题。
陪练完成后标记 corrected_needs_review，不直接标记 mastered。
经过 1-2 次复习练习独立答对后，题型才能升级为 mastered。
```

实施原则：

```text
1. 不再围绕“单题/多题”设计分支。
2. 不让 OCR/ASR 准确率阻塞核心学习资产模型。
3. 先做文本输入的统一 submission 闭环，再接拍照和语音。
4. 旧 /learning/session API 保留兼容，但新小程序主链路切到 /learning/submissions。
5. PostgreSQL 是学习资产主存储，RAG 不存孩子学习记录。
6. 每个阶段必须有测试和可验收的产品行为。
```

## 2. 总体依赖顺序

```text
S0 文档与口径锁定
-> S1 首页统一入口
-> S2 Submission 数据模型和 Store
-> S3 文本 Intake
-> S4 批量结构化、判题和初始沉淀
-> S5 错题队列和 Submission Graph
-> S6 Submission API
-> S6.5 account/family + child 数据隔离加固
-> S7 小程序确认页和错题队列体验
-> S8 掌握度、复习计划、家长反馈
-> S9 拍照/语音输入接入
-> S10 真实 DeepSeek + 小程序端到端评测
```

推荐严格按顺序推进。S2-S5 是后端资产模型核心，不建议跳过直接做 UI。

## 10. S6.5 account/family + child 数据隔离加固

目标：

```text
在 S7 小程序 UI 前先补牢真实小程序多人使用边界。
同一个家庭可以管理多个孩子，但每个孩子的学习资产、错题、证据、队列和报告必须独立。
任何学习资产写入不能只依赖前端传 child_id，必须通过后端 openid/session_token 授权。
```

设计口径：

```text
1. account：当前 v0.1 不引入完整账号密码体系，微信 openid 代表登录主体。
2. family：当前 v0.1 由 openid 派生最小 family_id，先满足家庭级数据边界。
3. child：一个 family 可绑定多个 child，每个 child 独立学习档案和错题资产。
4. session_token：API 鉴权凭证，解析出 openid 后再校验 openid-child binding。
5. 数据查询默认以 child_id 为主，family_id 是第二层归属边界，后续支持多家长共享家庭。
```

数据要求：

```text
1. children 写入 family_id。
2. child_bindings 写入 openid、child_id、family_id。
3. learning_sessions 写入 family_id。
4. wrong_questions 写入 family_id。
5. learning_submissions 写入 family_id。
6. learning_submission_items 写入 family_id。
7. mastery_evidence 写入 family_id。
```
