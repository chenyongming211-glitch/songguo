# v0.2 产品架构优化方案

## 1. 背景

当前松果AI已经具备可运行的产品骨架：

```text
微信小程序
  -> FastAPI 产品后端
    -> LearningSubmissionGraph
    -> MathMistakeTutorGraph
    -> LearningStore
    -> 家长报告 / 错题 / 学习沉淀 / 复习计划
```

代码层面已经完成了几个关键基础：

- 小程序不直接接大模型，只调用松果AI产品 API。
- `MathMistakeTutorGraph` 和 `LearningSubmissionGraph` 已经是真实 LangGraph compiled graph。
- 模型调用通过 LangChain Core ChatModel 适配层进入 OpenAI-compatible 模型。
- Store 层已经支持 SQLite、本地 InMemory 和 PostgreSQL。
- 后端测试、小程序合同测试和评测脚本已经形成基本回归网。

当前主要问题不是“架构方向错了”，而是要从本地 MVP 过渡到真实手机私测和后续多学科演进时，需要补齐安全、可靠性、可观测性和模块边界。

## 2. 架构判断

当前方向合理，应该继续沿用：

```text
前端薄入口
-> 产品后端控状态和安全
-> LangGraph 控制教学流程
-> LangChain Core 负责模型适配
-> Store 负责长期学习资产
```

不建议推倒重来，也不建议把后端改成自由发挥的通用 Agent。儿童学习产品必须保留受控流程、答案护栏、数据隔离和可审计学习沉淀。

## 3. 优化原则

1. **先安全私测，再扩能力。**
   后端一旦公网部署，接口安全优先级高于新功能。

2. **前端保持简单，后端变聪明。**
   小程序只负责拍照、输入、展示和交互；学科识别、题型识别、智能体路由都在后端完成。

3. **数学强链路不重写。**
   `MathMistakeTutorGraph` 是当前最成熟能力，短期只加路由接入和观测，不重做图内部。

4. **Graph 控流程，业务动作可审计。**
   LangGraph 适合组织步骤，但数据库写入、模型调用、文件保存等副作用必须逐步变得幂等、可追踪、可回放。

5. **评测先于扩学科。**
   新增语文、英语、自动路由前，必须有最小评测集和发布门禁。

## 4. 短期优化：真实手机私测前

目标：让项目可以安全地放到 HTTPS 后端上，支持你自己用真实手机拍照、上传、识别、陪练，而不暴露给其他人。

### 4.1 照片接口补齐授权

当前 `POST /api/v1/learning/photo-review` 上传时会校验 `child_id`，但读取和确认照片 review 时也必须按 `review.child_id` 校验。

需要整改：

- `GET /api/v1/learning/photo-review/{review_id}` 增加 `X-Session-Token`。
- `POST /api/v1/learning/photo-review/{review_id}/confirm` 增加 `X-Session-Token`。
- 读取 review 后调用统一 child 授权。
- 增加严格模式测试：其他 openid 不能读取或确认该 review。

验收：

```text
strict auth 下：
1. 无 token 读取 review 返回 401。
2. 其他 openid 读取 review 返回 403。
3. 其他 openid 确认 review 返回 403。
4. owner openid 可以读取和确认。
```

### 4.2 增加 openid 白名单

体验版小程序限制的是入口，不限制公网 API。私测阶段后端建议增加：

```text
SONGGUO_ALLOWED_OPENIDS=openid_a,openid_b
```

需要整改：

- 微信登录后检查 openid 是否在白名单。
- 非白名单 openid 返回 403。
- 本地 mock 模式不受影响，或通过显式 dev mode 放开。
- 系统状态接口不泄露白名单内容。

验收：

```text
1. 白名单 openid 可以登录并访问学习 API。
2. 非白名单 openid 不能获取有效 session token。
3. 本地测试仍可使用 WECHAT_MOCK_OPENID。
```

### 4.3 上传文件限制

拍照上传必须限制类型、大小和空文件。

短期建议：

```text
允许类型: image/jpeg, image/png, image/webp
最大大小: 5MB
空文件: 拒绝
文件名: 继续做安全清洗
```

需要整改：

- 在 API 层读取文件后立即校验大小。
- 在服务层校验 `content_type`。
- 识别失败时进入人工确认，不崩溃。

验收：

```text
1. text/plain 上传在真实照片接口返回 400。
2. 大于 5MB 返回 413 或 400。
3. 空文件返回 400。
4. 合法 jpeg/png/webp 正常进入 OCR。
```

### 4.4 小程序补重新登录能力

当前小程序启动时登录。如果第一次启动时后端地址还是本地 `127.0.0.1`，后面改为 HTTPS 后可能没有有效 token。

需要整改：

- 设置页增加“重新微信登录”。
- 保存后端地址后可提示重新登录。
- 401 且清 token 后，不应匿名重试真实严格接口，而应触发重新登录或提示。

验收：

```text
1. 设置 HTTPS 后端后可以手动重新登录。
2. 登录成功后设置页显示真实微信登录。
3. strict auth 下不出现无 token 匿名访问学习数据。
```

### 4.5 生产配置硬化

私测环境必须显式配置：

```text
PUBLIC_BASE_URL=https://api.example.com
WECHAT_APPID=真实 AppID
WECHAT_SECRET=真实 AppSecret
SONGGUO_SESSION_SECRET=强随机字符串
SONGGUO_AUTH_MODE=strict
SONGGUO_AGENT_RUNTIME=langgraph
SONGGUO_SESSION_RUNNER=llm
WECHAT_CONTENT_SAFETY_PROVIDER=wechat
```

建议补充：

- `check_production_readiness()` 检查 `SONGGUO_AUTH_MODE=strict`。
- 检查 `SONGGUO_AGENT_RUNTIME=langgraph`。
- 检查 PUBLIC_BASE_URL 是否是 HTTPS。
- 检查是否配置了 `SONGGUO_ALLOWED_OPENIDS`。

验收：

```text
1. 缺关键配置时系统状态显示 not ready。
2. 使用 http:// PUBLIC_BASE_URL 时出现 warning。
3. 未开启 strict auth 时出现 warning 或 missing。
```

## 5. 中期优化：稳定私测和快速迭代

目标：让真实手机私测中遇到的网络抖动、模型超时、重复提交、路由误判、成本不透明等问题可控。

### 5.1 OCR 改异步任务

同步 OCR 会受网络和视觉模型延迟影响。中期建议改为任务状态机：

```text
uploaded
-> processing
-> needs_confirmation | remediation_ready | graded_correct | failed
```

API 形态：

```text
POST /api/v1/learning/photo-review
GET  /api/v1/learning/photo-review/{review_id}
POST /api/v1/learning/photo-review/{review_id}/confirm
```

上传接口可以先返回 `review_id` 和 `status=processing`，小程序轮询状态。

### 5.2 幂等键

手机端常见问题是重复点击、弱网重试、上传超时但后端已处理。关键写接口应支持幂等。

优先覆盖：

```text
POST /photo-review
POST /photo-review/{review_id}/confirm
POST /submissions
POST /submissions/{submission_id}/tutor/attempt
POST /session/{session_id}/attempt
```

建议：

```text
Header: Idempotency-Key
范围: openid + endpoint + key
结果: 同 key 重放返回首次结果
```

### 5.3 Graph 节点副作用收束

当前 graph node 会直接创建 session、写 event、写 message、调用模型。MVP 可接受，但中期要把副作用变得可控。

建议分层：

```text
Graph Node:
  只决定下一步和输出意图

Action Layer:
  负责持久化、模型调用、文件保存、事件记录

Store:
  提供幂等写入和事务边界
```

短期不需要大重构，可以先从新建的学科路由和语文/英语图开始按这个边界写。

### 5.4 统一鉴权依赖

`learning`、`parent`、`reminders`、`artifacts` 中都有 child 授权逻辑。后续接口增加后容易漏。

建议新增统一 FastAPI dependency：

```text
require_session()
require_child_access(child_id)
require_review_access(review_id)
require_submission_access(submission_id)
```

收益：

- 所有路由复用同一套错误码。
- 新接口更难漏鉴权。
- strict auth 和 dev mode 的边界更清楚。

### 5.5 可观测性增强

当前已有 AI call log，但私测需要更完整的链路观测。

建议记录：

```text
request_id
openid hash
child_id
submission_id
review_id
session_id
graph_name
node_name
model provider
model name
latency_ms
token usage
fallback reason
error class
```

目标：

- 能定位“为什么这次拍照慢”。
- 能定位“为什么这道题走错智能体”。
- 能统计每天模型成本。
- 能复盘模型输出质量。

### 5.6 三学科评测门禁

配合 `v0.2-auto-subject-routing-plan.md`，中期必须从数学评测扩到三学科。

最小评测集：

```text
数学 50 题
语文 30 题
英语 30 题
模糊/不完整输入 20 条
```

门禁指标：

```text
学科路由准确率
题型识别准确率
答案泄露率
一次多问率
fallback 率
平均响应时间
模型成本
```

## 6. 长期优化：多学科学习平台

目标：从“能陪练几类题”升级为“围绕孩子长期学习画像的多学科学习系统”。

### 6.1 TutorGraph 流程库

长期应形成一组稳定图：

```text
MathMistakeTutorGraph
ChineseReadingTutorGraph
ChineseWritingTutorGraph
EnglishExpressionTutorGraph
EnglishGrammarTutorGraph
GeneralClarificationTutorGraph
ParentReportGraph
ReviewPlanGraph
```

每个图都有：

- 明确输入 schema。
- 明确输出 contract。
- 独立评测集。
- 独立 fallback 策略。
- 对应学习沉淀字段。

### 6.2 分学科知识体系

数学不是语文，语文不是英语。长期需要建立分学科知识体系：

```text
math:
  知识点、错因、题型、关键步骤、同类题。

chinese:
  阅读能力、表达完整度、证据定位、词句理解、作文结构。

english:
  词汇、语法、句型、翻译、语义表达、拼写。
```

这些能力最终统一进入孩子的学习画像。

### 6.3 学习画像驱动路由

后期路由不只看当前题，还应看孩子历史。

示例：

```text
同样一道应用题：
  孩子历史常错单位 -> 先追问单位。
  孩子历史常漏条件 -> 先追问题目条件。
  孩子历史常算错 -> 先追问计算步骤。
```

### 6.4 评测平台化

长期需要把评测从脚本升级为发布门禁：

```text
路由评测
OCR 评测
数学教学评测
语文评价评测
英语评价评测
家长报告评测
安全评测
成本评测
```

每次修改模型 prompt、路由、Graph 或 Store，都能看到质量变化。

### 6.5 隐私和合规

儿童学习产品长期必须补：

- 照片保留周期。
- 用户主动删除数据。
- openid 和日志脱敏。
- 模型请求最小化传输。
- 家长授权记录。
- 安全事件审计。
- 数据导出和删除机制。

### 6.6 服务边界演进

现在一个 FastAPI 服务足够。长期可以按压力拆：

```text
API 服务
OCR/视觉 worker
LLM worker
评测 worker
定时复习和消息 worker
```

不建议现在过早微服务化。先把模块边界、幂等、观测和任务模型做好。

## 7. 推荐执行顺序

### 7.1 第一阶段：私测安全闭环

```text
1. 照片读取和确认接口补授权。
2. openid 白名单。
3. 上传类型和大小限制。
4. 设置页重新登录。
5. 生产就绪检查增强。
```

### 7.2 第二阶段：稳定性和观测

```text
1. OCR 状态机和异步化。
2. 写接口幂等键。
3. 统一鉴权 dependency。
4. AI/OCR/Graph 链路观测。
5. 私测错误和成本报表。
```

### 7.3 第三阶段：多学科架构

```text
1. SubjectRouter。
2. HomeworkIntakeGraph。
3. ChineseBasicTutorGraph。
4. EnglishBasicTutorGraph。
5. GeneralClarificationTutorGraph。
6. 三学科评测集。
```

### 7.4 第四阶段：平台化

```text
1. 分学科知识体系。
2. 长期学习画像驱动教学。
3. TutorGraph 流程库。
4. 评测平台化。
5. 隐私合规和数据生命周期。
```

## 8. 与自动学科路由方案的关系

`v0.2-auto-subject-routing-plan.md` 解决“前端统一入口，后端自动识别和路由到不同学科智能体”的问题。

本文档解决更底层的产品架构问题：

```text
公网私测安全
拍照上传可靠性
Graph 副作用和幂等
统一鉴权
可观测性
评测门禁
长期平台边界
```

两份文档应一起执行：先补私测安全闭环，再落地自动学科识别和多智能体路由。

## 9. 当前结论

松果AI当前架构方向正确，不需要重写。短期最重要的是把真实手机私测安全做扎实；中期补异步、幂等、观测和统一鉴权；长期再扩展为多学科 TutorGraph 流程库和学习画像驱动的产品平台。
