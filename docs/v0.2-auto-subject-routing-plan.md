# v0.2 自动学科识别与智能体路由整改方案

## 1. 背景

当前小程序产品入口已经逐步从“数学错题”升级为“拍照、语音或输入作业后由松鼠博士陪练”。孩子和家长不应该先判断题目属于数学、语文还是英语，也不应该被要求选择具体题型。

当前后端已经具备较成熟的数学学习闭环：

```text
Learning Submission
-> LearningSubmissionGraph
-> MathMistakeTutorGraph
-> 判题、错因、同类题、LearningDeposit、家长反馈
```

但这一闭环的成熟能力仍主要集中在小学数学。语文、英语等学科还没有同等成熟的结构化识别、评价协议、专用 TutorGraph 和评测集。

本整改方案的核心目标是：**前端继续保持统一做题入口，后端自动识别学科和题型，再路由到对应智能体。**

## 2. 目标

### 2.1 产品目标

- 孩子只需要拍照、输入或语音提交作业。
- 小程序不要求孩子选择数学、语文、英语或具体题型。
- 后端自动识别学科、题型和任务意图。
- 数学继续走现有强闭环。
- 语文和英语先接入可控的轻量陪练闭环，再逐步增强。
- 家长端仍看到统一的学习记录、错因、薄弱点和复习建议。

### 2.2 技术目标

- 新增学科和题型自动识别层。
- 在 Learning Submission 流程中加入路由结果。
- 保留 `MathMistakeTutorGraph` 作为数学专用图。
- 新增语文、英语和通用澄清型 TutorGraph 的最小版本。
- 建立三学科路由评测和发布门禁。

## 3. 非目标

短期不做以下内容：

- 不要求小程序前端出现学科选择器。
- 不把所有学科强行套进数学判题模型。
- 不一次性完成完整语文作文大闭环。
- 不一次性完成完整英语语法体系。
- 不把后端改成自由发挥的通用 Agent。
- 不废弃现有数学 LangGraph 主链路。

## 4. 目标架构

```text
微信小程序
  -> Learning Submission API
    -> HomeworkIntakeGraph
      -> SubjectRouter
        -> MathMistakeTutorGraph
        -> ChineseReadingTutorGraph
        -> EnglishExpressionTutorGraph
        -> GeneralClarificationTutorGraph
    -> 学习记录 / 错题 / 表达问题 / 学习画像 / 家长报告
```

### 4.1 入口原则

小程序入口只表达用户动作：

```text
拍照作业
输入题目和孩子答案
语音识别后提交
开始陪练
```

前端可以展示“做题引导”“松鼠博士陪练”这类通用文案，但不要求孩子选择学科或题型。

### 4.2 后端路由原则

后端负责识别：

```text
subject: math | chinese | english | unknown
task_type: calculation | word_problem | reading_comprehension | sentence_rewrite | translation | grammar_fix | composition_fragment | unknown
confidence: 0.0 - 1.0
routing_reason: 简短可审计说明
router_version: 路由器版本
```

当识别置信度不足时，不直接猜测，而是进入澄清型陪练：

```text
这道作业我需要先确认一下：你是想让我检查答案、帮你改句子，还是一起理解题意？
```

## 5. 模块设计

### 5.1 HomeworkIntakeGraph

职责：

- 接收拍照、语音或文本提交。
- 统一解析出题目、孩子答案和上下文。
- 调用 `SubjectRouter` 得到学科和任务类型。
- 将路由结果写入 submission。
- 根据路由结果启动对应 TutorGraph。

边界：

- 不直接完成学科专属教学。
- 不直接生成长期复习计划。
- 不直接替代现有 `LearningSubmissionGraph` 的数学资产沉淀能力。

### 5.2 SubjectRouter

第一版采用规则优先、LLM 补充的混合方案。

规则特征：

```text
math:
  数字、算式、单位、应用题数量关系、几何、统计图、分数、小数、时间、金钱。

chinese:
  阅读短文、概括、中心思想、解释词语、造句、修改病句、作文片段、按要求写句子。

english:
  英文单词、英文句子、翻译、语法改错、时态、单复数、阅读选择、补全句子。
```

LLM 补充：

- 只在规则置信度不足时调用。
- 输出严格 JSON。
- 不生成教学内容，只做分类和理由说明。

建议输出结构：

```json
{
  "subject": "math",
  "task_type": "word_problem",
  "confidence": 0.91,
  "routing_reason": "题干包含数量关系、单位和至少需要多少辆的应用题问法。",
  "needs_clarification": false,
  "router_version": "subject_router_v0.1"
}
```

### 5.3 MathMistakeTutorGraph

继续作为数学主链路。

职责：

- 数学题结构化。
- 规则和模型混合判题。
- 错因识别。
- 防答案泄露。
- 同类题生成。
- LearningDeposit 和 MasteryEvidence 沉淀。

短期只做适配：

- 接收 `SubjectRouter` 的路由结果。
- 将 `detected_subject=math` 和 `detected_task_type` 记录到学习资产。
- 保持现有数学测试和黄金题集不退化。

### 5.4 ChineseBasicTutorGraph

短期最小能力：

- 判断题目是否为阅读理解、造句、词语解释、修改病句或作文片段。
- 不强行给唯一正确答案。
- 引导孩子回到题干或原文找依据。
- 对答案给出“是否回应题意、是否完整、是否表达清楚”的反馈。

示例教学策略：

```text
阅读理解:
  先问孩子答案依据来自原文哪一句。

造句:
  先检查句子是否完整，再看词语使用是否自然。

作文片段:
  先指出一个最关键的改进点，不一次性改完整篇。
```

短期输出：

```text
child_message
understanding_points
expression_feedback
next_revision_prompt
parent_summary
```

### 5.5 EnglishBasicTutorGraph

短期最小能力：

- 判断题目是否为翻译、造句、语法改错、单词拼写或阅读题。
- 不把英语题误判为数学题。
- 对孩子答案做轻量反馈。
- 引导孩子自己修正一个关键问题。

示例教学策略：

```text
翻译:
  先确认主语、谓语和关键词是否对应。

语法改错:
  先只指出一个最关键的语法点。

造句:
  先检查句子是否完整，再检查单词搭配。
```

短期输出：

```text
child_message
grammar_focus
vocabulary_focus
revision_prompt
parent_summary
```

### 5.6 GeneralClarificationTutorGraph

职责：

- 处理识别不确定、题目不完整、照片 OCR 质量差、孩子答案缺失等情况。
- 只问一个澄清问题。
- 不直接把不确定内容路由到数学图。

触发条件：

```text
subject = unknown
confidence < 0.65
question_text 为空
child_answer 为空且任务需要答案
拍照识别结果冲突
```

## 6. 数据模型调整

Learning Submission 建议新增字段：

```text
detected_subject
detected_task_type
subject_confidence
routing_reason
router_version
needs_clarification
```

Learning Item 建议新增字段：

```text
detected_subject
detected_task_type
evaluation_mode
```

`evaluation_mode` 取值：

```text
exact_answer       数学、拼写等可明确判对错
rubric_feedback    语文表达、英语表达等按评价维度反馈
clarification      信息不足，需要追问
```

## 7. API 调整

### 7.1 创建提交

`POST /api/v1/learning/submissions`

前端不再硬编码 `subject=math`。建议请求允许：

```json
{
  "child_id": "child_xxx",
  "subject": "auto",
  "grade": 3,
  "source_type": "text",
  "raw_text": "题目和孩子答案..."
}
```

后端响应增加：

```json
{
  "detected_subject": "chinese",
  "detected_task_type": "reading_comprehension",
  "subject_confidence": 0.86,
  "routing_reason": "题干要求根据短文回答原因。",
  "needs_clarification": false
}
```

### 7.2 拍照提交

`POST /api/v1/learning/photo-review`

OCR prompt 从“math homework”改为“student homework”。识别结果增加：

```text
subject_guess
task_type_guess
question_text
child_answer
work_steps_or_context
confidence
```

如果 OCR 不确定，直接进入人工确认或澄清图。

## 8. 分阶段实施计划

### 8.1 短期：自动识别和安全私测

目标：不破坏数学闭环的前提下，让后端能自动识别三学科并路由到最小可用智能体。

任务：

1. 去掉小程序提交页 `subject=math` 的硬编码，改为 `subject=auto`。
2. 新增 `SubjectRouter` 和路由结果模型。
3. 在 Learning Submission 创建流程中写入路由结果。
4. 数学继续路由到 `MathMistakeTutorGraph`。
5. 新增 `ChineseBasicTutorGraph` 最小实现。
6. 新增 `EnglishBasicTutorGraph` 最小实现。
7. 新增 `GeneralClarificationTutorGraph`。
8. 将拍照 OCR prompt 改为通用作业识别。
9. 增加照片读取、确认接口的 child 授权。
10. 增加三学科路由单元测试和小程序合同测试。

短期验收：

```text
1. 小程序不出现学科选择要求。
2. 数学题仍进入现有数学错题队列。
3. 语文阅读题不会进入数学图。
4. 英语句子题不会进入数学图。
5. 不确定题会问澄清问题。
6. 拍照接口在严格鉴权下不能读取或确认别人的 review。
```

### 8.2 中期：分学科评价协议

目标：让语文和英语不只是 fallback，而是拥有自己的评价协议和学习沉淀。

任务：

1. 建立统一 Tutor Contract：

```text
child_message
answer_unlocked
next_action
learning_deposit_delta
safety_check
parent_summary
```

2. 数学继续使用“对错、错因、同类题、掌握证据”。
3. 语文使用“理解要点、证据定位、表达完整度、修改建议”。
4. 英语使用“语法焦点、词汇焦点、语义准确性、修改建议”。
5. 家长报告支持按学科聚合。
6. 学习画像支持跨学科薄弱点。
7. 建立三学科 golden set。

中期验收：

```text
1. 三学科都有独立测试集。
2. 语文题不会被强行判唯一数值答案。
3. 英语题能指出一个关键语法或表达问题。
4. 家长报告能区分数学错因、语文表达问题、英语语法问题。
5. 路由准确率达到可私测标准。
```

### 8.3 长期：多学科学习系统

目标：从题目路由升级为学习画像驱动的多学科学习陪练系统。

任务：

1. 建立分学科知识图谱。
2. 建立孩子长期能力画像。
3. 根据历史薄弱点动态选择追问策略。
4. 建立 `IntakeAgent`、`SubjectRouterAgent`、`TutorAgent`、`EvaluatorAgent`、`ParentReportAgent` 的多智能体协作边界。
5. 拍照 OCR、作文反馈、周报生成异步任务化。
6. 建立发布前自动评测门禁。
7. 增加数据保留、删除、脱敏和儿童隐私合规机制。

长期验收：

```text
1. 系统能稳定处理数学、语文、英语常见小学作业。
2. 不同学科的学习沉淀进入统一学习画像。
3. 家长报告能解释孩子在不同学科上的主要薄弱点。
4. 新学科接入只需要新增路由规则、TutorGraph 和评测集。
```

## 9. 测试要求

### 9.1 路由测试

至少覆盖：

```text
数学计算题
数学应用题
语文阅读理解
语文造句
语文修改病句
英语翻译
英语语法改错
英语造句
不完整题目
OCR 低置信度结果
```

### 9.2 回归测试

必须保证：

```text
现有数学 golden set 不退化
MathMistakeTutorGraph compiled graph 测试不退化
LearningSubmissionGraph compiled graph 测试不退化
小程序合同测试不退化
严格鉴权测试不退化
```

### 9.3 私测验收样例

```text
拍照数学应用题:
  自动识别 math / word_problem，进入数学错题队列。

拍照语文阅读题:
  自动识别 chinese / reading_comprehension，追问原文依据。

拍照英语改错题:
  自动识别 english / grammar_fix，只指出一个关键语法点。

拍照模糊作业:
  自动进入澄清流程，不胡乱判题。
```

## 10. 风险和约束

### 10.1 路由误判

风险：语文题被误判为数学，或英语题被误判为语文。

控制：

- 置信度不足时进入澄清。
- 记录 `routing_reason` 方便复盘。
- 建立路由评测集。

### 10.2 语文和英语评价过度绝对化

风险：把开放题当成唯一答案题处理。

控制：

- 语文、英语默认使用 rubric feedback。
- 只有拼写、选择题、明确填空题才使用 exact answer。

### 10.3 数学链路被改坏

风险：新增路由层影响现有数学强闭环。

控制：

- 数学 graph 不重写，只在前面加路由。
- 所有数学黄金评测必须保持通过。

### 10.4 前端重新复杂化

风险：为了路由而把学科选择压力转移给孩子。

控制：

- 前端不新增必选学科。
- 学科识别结果可以作为内部状态或家长端解释，不作为孩子操作前置条件。

## 11. 推荐落地顺序

```text
1. 文档和需求基准更新。
2. SubjectRouter 数据模型和单元测试。
3. Learning Submission 写入路由结果。
4. 小程序提交 subject=auto。
5. 数学链路接入路由结果但不改图内部。
6. ChineseBasicTutorGraph 最小版本。
7. EnglishBasicTutorGraph 最小版本。
8. GeneralClarificationTutorGraph。
9. OCR prompt 通用化。
10. 三学科私测用例和评测报告。
```

## 12. 当前结论

前端统一入口是正确方向。后端不应该继续假设所有提交都是数学题，也不应该让孩子承担学科和题型判断。正确的下一步是把“自动学科识别和智能体路由”作为 v0.2 的核心架构整改，在不破坏数学强链路的前提下，逐步扩展到语文和英语。
